# Project Guidelines & Operating Rules

## 1. Strict Scope & Request Adherence
- **Do Not Invent New Systems**: Never introduce unrequested features, UI widgets, buttons, toggles, external mechanics, or architectural layers unless explicitly requested by the user.
- **Minimal, Direct Implementations**: Address the exact problem statement using the simplest direct fix. Do not expand scope or add unsolicited "polish".

## 2. Handling Uncertainty & Preventing Hallucination
- **Technical & External Doubts**: When in doubt regarding browser behaviors, specifications, library quirks, or external APIs, search the web rather than guessing.
- **Project & Requirement Doubts**: When in doubt regarding the project, features, user intent, or architecture, **ask the user directly** rather than making assumptions or hallucinating answers.

## 3. Code Style & Formatting
- **No Comments**: Do not write comments in code files (no inline, block, or explanatory comments).
- **Pure Code & Clean Indentation**: Produce strictly pure, well-structured, properly indented code.

## 4. Engineering Rigor & Anti-Vibecoding
- **No Vibecoding or Speculative Code**: Never produce code based on guesswork, superficial patterns, or vague assumptions.
- **Intentional & Disciplined Logic**: Every implementation must be deliberate, technically sound, and mathematically/logically verified.
- **No Superficial Hacks**: Avoid haphazard patches, bloated wrapper layers, or speculative workarounds. Focus on root causes with clean, robust solutions.

## 5. Git & Push Policy
- **Push Cadence**: Always commit and push changes to the remote repository upon completing tasks.
